## P0-1. Произвольная запись файлов на диск через `Content-MD5` (исправлено)

`server/src/api/routes.ts` передаёт заголовок `Content-MD5` в
`LocalContentStorage.savePackage()` как **имя каталога**, без какой-либо проверки
(`server/src/api/storage.ts`, `savePackage`):

```ts
const packageHash = hash ?? LocalContentStorage.hash(data);
const folder = path.join(this.packagesDir, packageHash);
fs.mkdirSync(folder, { recursive: true });
fs.writeFileSync(path.join(folder, safeName), data);
```

Санитизируется только имя файла (`path.basename`), а хэш — нет.

Воспроизведение (сервер на `:8080`):

```bash
curl -X POST http://127.0.0.1:8080/api/v1/content/packages \
  -H 'Content-Type: multipart/form-data; boundary=X' \
  -H 'Content-MD5: ../../../../../../tmp/si-evil' \
  --data-binary $'--X\r\nContent-Disposition: form-data; name="file"; filename="pwn.siq"\r\n\r\nDATA\r\n--X--\r\n'
```

Ответ `200`, тело `/api/v1/content/packages/../../../../../../tmp/si-evil/pwn.siq`, и файл
реально появляется в `/tmp/si-evil/pwn.siq`.

Следствия:
- запись произвольного файла в любой каталог, доступный процессу (перезапись конфигурации,
  перезапись `dist/index.html`, размещение своего содержимого вне каталога данных);
- при запуске от привилегированного пользователя — компрометация машины;
- сервер по умолчанию слушает `0.0.0.0`, то есть доступен всей локальной сети.

**Что сделать.** Никогда не использовать клиентские значения как путь. Хэш вычислять самому
(как делает `LocalContentStorage.hash`) либо валидировать строго
`/^[A-Za-z0-9_-]{8,64}$/`, а результат нормализовать и проверять `path.resolve(...).startsWith(root)`.
То же касается `saveAvatar` (там хэш вычисляется, но функция должна оставаться единой точкой
безопасного сохранения). Нужны тесты: `..`, `%2e%2e`, абсолютные пути, разделители Windows,
юникод-нормализация.

## P0-2. Чтение произвольных файлов через `/api/v1/content/{packages,avatars}` (исправлено)

`getPackagePath`/`getAvatarPath` вызывают `getSafePath`, где `path.basename` применяется к имени
файла, но **не к хэшу-каталогу**:

```ts
return this.getSafePath(path.join(this.packagesDir, hash), name);
```

Воспроизведение:

```bash
curl "http://127.0.0.1:8080/api/v1/content/packages/..%2F..%2F..%2F..%2F..%2F..%2Fetc/passwd"
# root:x:0:0:root:/root:/bin/bash ...

curl "http://127.0.0.1:8080/api/v1/content/avatars/..%2F..%2F..%2F..%2F..%2F..%2Fetc/passwd"
# то же самое
```

Читается любой файл, который доступен процессу на чтение.

**Что сделать.** Общий помощник «безопасный путь внутри каталога» (нормализация + проверка
префикса + проверка `isFile`), применённый и к `hash`, и к `name`, и к медиа-пути
(`getMediaPath` уже проверяется корректно — на него можно опираться как на образец).
Добавить регрессионные тесты на оба маршрута и на `/package/...`.

## P0-3. Загрузка активного HTML на тот же origin + iframe с `allow-same-origin` (исправлено)

`POST /api/v1/content/avatars` и `POST /api/v1/content/packages` принимают **любой** файл и
отдают его обратно с типом по расширению:

```bash
# загрузили evil.html, получили
# /api/v1/content/avatars/<hash>/evil.html
curl -D- .../evil.html
# Content-Type: text/html; charset=utf-8
# <html><body><script>alert(document.domain)</script></body></html>
```

`src/components/gameTable/HtmlContent/HtmlContent.tsx` рендерит HTML-контент пакета в iframe с
`sandbox='allow-scripts allow-same-origin allow-presentation'`, а в комментарии прямо записано:
«allow-scripts & allow-same-origin combination is safe until we serve parent and iframe content from
different origins». Локальный сервер как раз раздаёт родительскую страницу, API и медиа с одного
origin, поэтому сочетание флагов позволяет содержимому iframe дотянуться до `parent`/`opener`,
до `localStorage` и к API сервера (включая привилегированные вызовы от имени вошедшего).

**Что сделать (варианты, желательно оба):**
1. Раздавать пользовательский контент с отдельного origin (отдельный порт/поддомен) либо через
   `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` для типов, которые не
   должны открываться inline (HTML/JS/SVG);
2. убрать `allow-same-origin` из `HtmlContent` (и проверить `MediaItem`), оставив передачу
   данных через `postMessage` — сейчас оно и так используется;
3. ограничить загрузку аватаров списком расширений и проверять сигнатуру.

## P0-4. Лобби и раздача всего содержимого без какой-либо аутентификации (частично исправлено)

Все REST-маршруты и оба хаба доступны анонимно; нет ни токена, ни cookie-сессии, ни привязки
к адресу. В доверенной домашней сети это осознанный компромисс, но:

- `docs/local-server.md` и README не предупреждают, что сервер нельзя выставлять в интернет;
- `getPackagePath`/`getMediaPath` позволяют скачать любой загруженный пакет целиком;
- пароль комнаты (`joinPassword`) хранится и сравнивается в открытом виде и передаётся в
  запросе как есть.

**Что сделать.** Как минимум — предупреждение в README/CLI-логе при `host=0.0.0.0`; отдельный
флаг «только localhost» по умолчанию. Как максимум — модель локальной идентичности (P0 в
`docs/current-game-state-and-roadmap.md`): краткоживущий токен комнаты, привязка места к
подтверждённой личности, PIN не детерминированный по ID.

## P1-1. `npm run test:server` падает без предварительно запущенного сервера (исправлено)

`package.json` → `test:server` запускает `node server/scripts/*.js` без поднятия сервера, а скрипты
по умолчанию идут на `http://localhost:8080`. В чистом окружении получаем:

```
Seats test failed:
TypeError: fetch failed  [cause]: AggregateError [ECONNREFUSED]
```

Это скрытая зависимость от ручного шага, из-за которой команда непригодна для CI и для нового
разработчика. При этом `seats-test.js` вызывает `process.exit(1)`, а `access-test.js` только
`process.exitCode = 1` — поведение несогласовано (второй может «провалиться молча» в цепочке `&&`,
если открытые сокеты удержат цикл; сейчас маскируется тем, что скрипты закрывают соединения).

**Что сделать.** Обёртка `server/scripts/run-all.js`: поднять сервер на свободном порту
(`SI_PORT=0`), дождаться `/health`, прогнать сценарии с `SI_BASE_URL`, гарантированно погасить
процесс и вернуть агрегированный код. Привести все скрипты к `process.exitCode = 1` (без
`process.exit`) и добавить таймауты на ожидание.

## P1-3. CI не проверяет то, что объявлено обязательным (исправлено частично)

`.github/workflows/build.yml`: `npm install` → `npm test` → `npm run build-prod`.
Нет `npm run lint`, нет проверки типов сервера (`tsc -p server/tsconfig.json`), нет
`npm run test:server`. При этом `AGENTS.md` требует и сборку, и тесты, и линт. CodeQL, Playwright
и release-пайплайны используют `actions/*@v2/v3` и Node 24 без фиксации; `.eslintignore` исключает
`e2e`, поэтому E2E-код не проверяется.

Отдельно: `.github/workflows/playwright.yml` запускает `npm run test:e2e`, но сами тесты
(`e2e/game-flow.spec.ts`) почти целиком состоят из `if (await ...isVisible()) { ... }` и
`expect(gameElements).toBeGreaterThanOrEqual(0)` — то есть проходят при любом поведении приложения
и не проверяют ни вход, ни создание игры, ни ход партии. Единственное жёсткое утверждение —
снапшот главной страницы.

**Что сделать.** Добавить в `build.yml` шаги `lint`, `tsc -p server/tsconfig.json`, поднять сервер и
прогнать `test:server`. E2E переписать на реальный сценарий: имя → лобби → создание игры из
библиотеки → старт → ответ на вопрос, с проверкой сообщений сервера.

## P1-4. Docker-образ для веб-клиента не содержит сервер и ломает SPA-роутинг

`Dockerfile`:

```
FROM nginx:alpine
COPY dist/* /usr/share/nginx/html/
```

- локальный сервер (`server/`) в образ не попадает, поэтому «локальная игра» в контейнере
  невозможна, хотя `docs/local-server.md` описывает именно такой сценарий;
- `COPY dist/*` не копирует скрытые файлы и падает/теряет содержимое, если `dist` не собран;
- нет конфигурации `try_files $uri /index.html`, а клиент использует history API
  (сервер сам делает fallback — nginx этого не делает), значит прямой заход на внутренний маршрут
  даст 404.

**Что сделать.** Либо многоступенчатый образ `node` → сборка → запуск `server/src/index.ts`,
либо отдельный `Dockerfile.server`; для статического варианта — свой `nginx.conf` с SPA-fallback.

## P1-5. Пин-код игры выводится из ID игры

`server/src/game/game.ts`:

```ts
private getPin(): number { return 100000 + (this.id * 7919) % 900000; }
```

PIN однозначно вычисляется из последовательного `id`, который открыто отдаётся в
`GET /api/v1/games/list`. Для локальной сети риск невелик, но «вход по PIN» перестаёт быть
сколько-нибудь секретным, а при перезапуске сервера PIN-ы повторяются.

**Что сделать.** Случайный PIN (`crypto.randomInt`), проверка на уникальность среди активных игр,
ротация при перезапуске. В идеале — PIN с истечением срока.

## P1-6. Автоматическая игра не получает имя игрока (исправлено)

Клиент (`src/state/online/onlineActionCreators.ts` → `createNewAutoGame`) отправляет только
`culture`, а `server/src/api/routes.ts` берёт имя из query-параметра:

```ts
const playerName = request.query.player?.toString() || 'Игрок';
```

Тело `RunAutoGameRequestModel` игнорируется (`void body`). В итоге игрок, нажавший «играть одному»,
входит в игру под именем «Игрок», а не под своим логином; при двух таких игроках возможна коллизия
имён (второй получит другое место/ошибку). Серверные скрипты этого не ловят, так как сами
передают `?player=`.

**Что сделать.** Читать имя из тела запроса, оставив query как fallback; добавить проверку
уникальности имени и тест «два автоматических входа подряд».

  путь «сокет умер до handshake»).
