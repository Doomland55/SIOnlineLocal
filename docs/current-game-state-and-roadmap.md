# Состояние локальной игры и план доработки

Срез: код SIOnlineLocal после `22df9ce` с доработкой устного ответа и подсказок ведущему ветки `arena/7fefa702-sionlinelocal`. Документ описывает именно локальный сервер и встроенный веб-клиент, а не официальный SIOnline. Последняя проверка этого среза: 447 тестов Jest прошли на `22df9ce`, один пропущен; `build-dev`, серверный TypeScript и `test:server` прошли; `lint` завершился с 95 ошибками и 566 предупреждениями. `--forceExit` использовался для Jest, поэтому чистое завершение всех ресурсов не подтверждено.

**Главное:** основная локальная партия работает в проверенных сценариях, но это **не полная реализация правил и протокола SI**. Значение настройки в окне правил ещё не означает, что соответствующая механика реализована. Не считать тесты доказательством совместимости каждого SIQ и каждого клиента.

- [Первоначальный аудит с источниками](server-vs-desktop-audit.md) относится к **старому коммиту `a87e1f2`**. Часть его дефектов уже исправлена; не переносить его утверждения в текущий backlog без повторной проверки.
- Сравнение ниже опирается на [исходники десктопной SI, зафиксированные на `1424281e0d13ae1192892365e32a28f1e7aefb40`](https://github.com/VladimirKhil/SI/tree/1424281e0d13ae1192892365e32a28f1e7aefb40/src). Конкретный исторический релиз пользователем не задан; это не проверка совместимости со всеми версиями SI и не тест двух запущенных приложений.

## 2. Архитектура и запуск

```text
Браузер: React/Redux + SIHostClient/GameServerClient
    │ HTTP /api/v1/*              │ SignalR MessagePack /sionline, /sihost
    ▼                             ▼
server/src/api/routes.ts     server/src/hubs/{sionlineHub,siHostHub}.ts
    └──────────────► Lobby (комнаты) ──► Game + GameSession (правила)
                          │                    │
                    package/library       protocol.ts, questionPlan.ts
                          └─────► файлы SIQ и медиа по HTTP
```

Ключевые места:

| Путь | Назначение |
|---|---|
| `server/src/index.ts`, `config.ts` | HTTP/SignalR, запуск и настройки сервера. |
| `server/src/game/lobby.ts`, `session.ts`, `game.ts` | Жизненный цикл комнат и мест, состояние партии, решения, таймеры, финал. |
| `server/src/game/questionPlan.ts`, `package.ts`, `library.ts` | План содержимого, библиотека, загрузка/распаковка SIQ и разрешение медиа. |
| `server/src/api/routes.ts`, `server/src/hubs/` | Локальный REST и SignalR, вход и протокол. |
| `src/model/siquester/packageLoader.ts` | Модель и преобразование пакетов SIQ v4/v5. |
| `src/client/game/`, `src/logic/messageProcessor.ts`, `src/logic/ClientController.ts` | Клиентские команды, разбор событий и обновление интерфейса. |
| `src/state/room2Slice.ts`, `src/state/tableSlice.ts` | Состояние участников, решений, таймеров и отображения. |
| `src/components/gameTable/AudioContent/`, `VideoContent/` | Проигрывание медиа и сообщения о завершении. |

Обычный локальный запуск (Node.js и npm уже установлены):

```bash
npm ci
npm run make-test-package   # если нужен минимальный тестовый пакет
npm run build-local         # клиент с конфигурацией локального сервера
npm run server              # по умолчанию 0.0.0.0:8080
```

Либо `npm run serve-local` собирает локальный клиент и запускает сервер. Пакеты кладутся в `server/packages/`; загруженные данные и распакованное медиа — в `server/data/`. Игры по умолчанию создаются по запросу клиента; `startupGames: true` включает создание игр для пакетов при запуске. `server/config.json.example` и `docs/local-server.md` описывают конфигурацию. Собранные файлы, зависимости, пользовательские пакеты и медиа не добавлять в коммит без отдельной необходимости.

## 3. Что уже работает в проверенных сценариях

| Область | Текущее поведение и границы |
|---|---|
| Комнаты и сеть | Создание игры по REST, библиотека/загрузка пакетов, PIN, роли ведущего/игрока/зрителя, готовность, лобби, чат и SignalR через WebSocket/MessagePack. Есть локальные настройки пароля и запрета зрителей, но это не полноценная защита от недоверенных пользователей. |
| Места и управляющий | Управляет живой ведущий, иначе создатель или первый подключённый человек. Место освобождается при выходе; возврат прежнего счёта возможен по имени, если место свободно. Пустая комната удаляется; у новой комнаты есть время на первое подключение. Во время обычного вопроса разрушительные изменения мест откладываются, в финале их поддержка ограничена. |
| Аватары | `image` и `video` хранятся раздельно, транслируются и повторяются после `INFO2` новому участнику; клиент не стирает известный аватар при повторном добавлении аккаунта. |
| Обычный вопрос | Таблица сохраняет темы и цены пакета, использованный вопрос помечается `-1`. Игрок или ведущий выбирает вопрос; `SETCHOOSER` передаёт право выбора. Если выбирающий бездействует, сервер делает выбор сам. Ведущий может выбрать вопрос за игрока. |
| Ответ и пас | После показа контента идёт `TRY`; только нажавший получает `ANSWER`. Повторные и чужие ответы/черновики ограничены. Неверный ответ учитывает штраф, `noRisk` — без штрафа; если отвечать больше некому или таймер нажатия истёк, показывается правильный ответ. Метки вариантов сохраняются и проверяются; поддерживается и прежний вариант пакетов с ответом-текстом. |
| Устная игра | Игрок нажимает кнопку и отвечает голосом без поля ввода. Управляющий сразу получает `ASK_VALIDATE` и оценивает ответ через `VALIDATE`; ведущий получает ответы пакета приватно. Окно проверки человека **не закрывается автоматически**, «Дальше» не завершает проверку. Если ведущий — бот, управляющий-игрок оценивает ответ вручную без раскрытия ему подсказки; боты проверяются автоматически. |
| Время и переходы | Сервер отслеживает срок раунда и основной ожидающий шаг. Пауза замораживает шаги и передаёт прошедшее время трёх клиентских таймеров. `MOVE 1` завершает текущий ожидающий шаг, `MOVE 3` выбирает раунд; пауза блокирует переходы. После истечения срока раунда текущий вопрос доигрывается. |
| Медиа | Пакетные медиа раздаются по HTTP; учитываются кодирование имён, регистр и Unicode, длинные имена безопасно сохраняются. Для аудио/видео **ответа** без явной длительности ожидается `ATOM` с типом и адресом либо резервные 180 секунд; медиа с длительностью ждёт её. Это не полная синхронизация всех устройств и не аналогичная обработка медиа вопроса. |
| Финал | Есть очередное удаление тем, участники с положительным счётом, закрытые ставки в пределах счёта, общий сбор ответов и автоматическое начисление. Неприсланная ставка становится 1. Черновики и ставки до раскрытия не рассылаются как открытые значения. Это упрощённый финал, см. раздел 5. |
| Начальные правила | `appSettings` при создании и часть `SET_OPTIONS` сохраняются и приходят через `OPTIONS2`; устный режим, скорость чтения и некоторые тайминги реально используются. Часть остальных опций пока только хранится/отображается. |

Отмеченные сценарии подтверждены существующими unit-тестами и/или скриптами, но не ручной партией на всех браузерах и не запуском десктопной SI рядом с локальным сервером.

## 4. Важные инварианты для следующих изменений

1. В устной игре не открывать поле ответа вообще; в обычной — не открывать его без нового нажатия, в том числе на следующем вопросе, после неверного ответа и переподключения. Ответ принимает только текущий отвечающий; финальный одновременный сбор — отдельная фаза.
2. Не закрывать автоматически окно проверки ответа **подключённого живого ведущего**. Серверный таймер раунда или кнопка «Дальше» не должны прерывать эту проверку. Проверка управляющим-игроком тоже не должна закрываться по таймеру.
3. Пауза останавливает серверные шаги, визуальные таймеры и воспроизведение; снятие продолжает с оставшегося времени. Не исполнять решения пользователей во время паузы.
4. Таймер раунда независим от таймеров вопроса/решений и не обрывает текущий вопрос. Старые callbacks, повторные сообщения и действия ботов не должны срабатывать на новом шаге.
5. `MOVE 1` завершает именно текущий ожидающий шаг и запускает тот же переход, что его нормальное окончание. Явный выбор раунда — другое действие.
6. После неверного ответа и/или пасов при отсутствии тех, кто может отвечать, заканчивается ожидание, но правильный ответ и его контент всё равно показываются.
7. Аватары и очки не должны пропадать при обновлении состава; секретные ответы/ставки финала не должны раскрываться до соответствующей фазы.
8. Цена берётся из пакета. Одинаковые цены вопросов сами по себе не являются ошибкой: пользователь подтвердил такой пакет.

## 5. Недоделки, различия с SI и порядок работ

Приоритеты ниже — рекомендация для разработчика, а не обещание сроков. «Сверить» означает, что точный эквивалент SI ещё нужно подтвердить на закреплённом эталоне и тестовых пакетах. Каждая задача должна иметь отдельные проверяемые сценарии и не нарушать инварианты раздела 4.

### P0. Безопасность доступа и надёжность восстановления

**Сейчас.** Пароль комнаты и `allowViewers` проверяются при входе, право управления ограничено. Однако подтверждения личности нет: возврат места привязан к имени, PIN детерминирован по ID. `isPrivate` и режим входа не дают полной эквивалентности официальной системе; `SETJOINMODE` игнорируется. `sendFullState`/`onReconnect` восстанавливают базовое состояние и некоторые персональные запросы, но не полный текущий атом, варианты, таймеры и состояние паузы для всех фаз. Последний человек выходит — комната удаляется.

**Отличие/риск.** В эталоне есть более полные проверки доступа и состояния; локальный сервер предназначен для доверенной сети. Пароль сам по себе не гарантирует защиту имени и места. Не открывать его недоверенной сети как защищённый сервис.

**Что сделать.**
1. Определить модель локальной идентификации, авторизации и срока жизни комнаты, не полагаясь только на имя или PIN. Явно документировать угрозы и хранение секретов.
2. Сверить ограничения роли, приватности и `SETJOINMODE` с [обработчиками Game.cs в SI](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/SICore/SICore/Clients/Game/Game.cs). Запрещённые команды должны отклоняться до изменения состояния.
3. Описать снимок состояния по фазам и восстанавливать его адресно: содержимое, таймеры и паузу, выбор, ввод, ожидающую проверку, финальные ставку/ответ. Не повторять уже завершённые запросы и не раскрывать секреты финала.
4. Тесты: отключение/повторный вход выбирающего, отвечающего, ведущего и зрителя до/во время/после решения и в финале; новая персона занимает освободившееся место; подмена имени; истечение таймеров при отключении; последняя связь комнаты.

### P1. Специальные вопросы и пользовательские скрипты SIQ

**Сейчас.** Типы пакета сообщаются через `QTYPE`, но обычная последовательность применяется почти ко всем вопросам. `noRisk` учитывает отсутствие штрафа; аукцион, «кот» и другие специальные сценарии в полной форме не реализованы. Модель/загрузчик не исполняют произвольный `<script>` SIQ v5.

**Эталон.** См. [ScriptsLibrary.cs](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/Common/SIPackages/ScriptsLibrary.cs) и [QuestionEngine.cs](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/Common/SIEngine.Core/QuestionEngine.cs). Импорт v4 преобразует старые типы в новые, но одно преобразование не реализует их механику.

**Что сделать.**
1. Составить таблицу типов (`stake`, `secret`, `secretPublicPrice`, `secretNoQuestion`, `stakeAll`, `forAll`, `noRisk` и др.) и для каждого зафиксировать права, шаги, ставки, тайм-ауты и сообщения.
2. Ввести явные фазы/решения для ставок, выбора игрока и стоимости; реализовать `ASK_SELECT_PLAYER`/`SELECT_PLAYER`, не смешивая их с выбором вопроса или финальными ставками.
3. Не разыгрывать неизвестный тип или скрипт как обычный без предупреждения: до поддержки показывать понятное ограничение/отказ.
4. Для каждого сценария добавить маленькую SIQ-фикстуру и тесты: несколько людей, боты, запрет чужих и повторных решений, границы ставки, таймаут, пауза, выход участника, «Дальше» и итоговый счёт.

### P1. Финальный раунд и проверка ответов

**Сейчас.** Базовая последовательность финала и скрытый сбор реализованы, но проверка финальных ответов автоматическая, без ручного решения живого ведущего. Очерёдность тем и проигрывание всех вопросов/тем не покрывают все варианты SI; равенство очков разрешается локальным порядком мест. Отправляется `PERSONFINALANSWER`, которого нет в перечислении входящих сообщений веб-клиента. При обычной игре текст сравнивается после нормализации без полной SI-проверки; числовое отклонение и ответы-точки не реализованы. Коэффициент `VALIDATE` не применяется к начислению.

**Эталон.** См. [GameController.cs: проверка ответа](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/SICore/SICore/Clients/Game/GameController.cs#L3252), [AnswerChecker.cs](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/SICore/SICore/Clients/Other/AI/AnswerChecker.cs), а также правила/финал в первоначальном аудите.

**Что сделать.**
1. Сверить права на участие, порядок при равных очках, все режимы финала, границы и раскрытие ставок, обработку пустых ответов и черновиков.
2. Добавить отдельную очередь ручной проверки финала и корректное раскрытие каждому клиенту. Не применять автоматическое закрытие окна живого ведущего.
3. Реализовать типы и точность проверки (текст/число/точка/вариант), коэффициенты и единое начисление; не подменять ответ правильной меткой без понимания `answerType`.
4. Тесты: минимум два человека и бот, разные/пустые/неоднозначные ответы, неверная/повторная ставка, ничья, реконнект, пауза и отсутствие утечки до раскрытия. Сверить `PERSONFINALANSWER` с реальным клиентом прежде чем менять формат.

### P1. Медиа, атомы и синхронизация

**Сейчас.** У вопроса `buildContentAtoms` подставляет медиа без длительности 3 секунды; `ATOM` используется только для медиа **ответа**. В финальном контенте ожидание `waitForFinish` обрабатывается не полностью. Для ответа используется первое совпадение типа/URI от подключённого участника; при одинаковых повторных URI протокол не различает устаревшее окончание и текущее воспроизведение. Есть 180-секундный fallback.

**Эталон.** SI ожидает завершение подходящего медиа и применяет отдельные ограничения/настройки времени показа; см. [GameController.cs](https://github.com/VladimirKhil/SI/blob/1424281e0d13ae1192892365e32a28f1e7aefb40/src/SICore/SICore/Clients/Game/GameController.cs#L670) и исходный аудит §12.

**Что сделать.**
1. Разделить показ атома, наличие явно заданной длительности, `waitForFinish`, предзагрузку и событие окончания; применить одинаково к обычному вопросу, ответу, финалу и фоновому аудио.
2. Сверить ожидаемого отправителя и способы идентификации текущего показа. Не считать URI уникальным идентификатором шага; если протокол не позволяет различить повторы, явно описать ограничение и безопасную стратегию.
3. Проверить, что `MOVE`, таймаут, пауза, ошибка загрузки, autoplay и отключение клиента завершают только нужный шаг, не оставляя старых callbacks. Тестировать больше одного браузера и разные задержки.
4. Добавить фикстуры: длинное видео/аудио в вопросе и ответе, несколько атомов с одинаковым URI, явная длительность, `waitForFinish=false`, HTML, многострочный текст и клиент, не приславший `ATOM`.

### P1–P2. Правила, таймеры и действия ведущего

**Сейчас.** Начальные значения видны и часть используется. Однако `managed`, `falseStart`, `partialText`, `partialImages`, `useApellations` и другие настройки не реализуют полную механику; начальная передача поддерживает не все поля клиента. `SET_OPTIONS` обрабатывает одну пару. `_deltaTime` нажатия не используется: конкурентное нажатие/фальстарт/блокировка не соответствуют полноценной SI. Визуальная пауза и выбор шага покрыты тестами, но переподключение посреди них остаётся отдельной задачей.

**Что сделать.**
1. Для каждого поля `ServerAppSettings` и `ServerTimeSettings` указать: источник, диапазон/единицы, фактическую семантику, значение по умолчанию, поддержку и сценарий теста. Не объявлять опцию работающей только по `OPTIONS2`.
2. Сверить фальстарт, интервал приёма нажатий, частичный показ и действия устного режима с эталоном; реализовывать по отдельности с тестами на одновременные нажатия и сетевые задержки.
3. Явно представить состояние текущего решения и его поколение; любой таймер должен выполнять действие только один раз и только для своей фазы. Проверить приоритет паузы, `MOVE`, `ATOM`, сетевого события и таймаута.
4. Протестировать обычную игру и финал на паузе в каждом шаге, включая решение ведущего и возврат клиента; сверить времена в секундах и протокольных десятых долях секунды.

### P2. Полнота команд, статистика и интеграция

**Сейчас.** Перечень команд и ограничений — [сверка протокола](client-server-protocol-audit.md). Не реализованы `SELECT_PLAYER`, `BAN`, `UNBAN`, `CHANGE`, `SETHOST`, `TOGGLE`, `MARK`, `REPORT`, `LEADERBOARD`, `APELLATE`; `MEDIALOADED` и `SETJOINMODE` игнорируются, `MOVEABLE` упрощён. `ISRIGHT` направляется в обработчик другого формата (`VALIDATE`). Апелляции и пересчёт результатов отсутствуют. `GAME_STATISTICS` содержит заглушечные значения; некоторые REST-методы статистики тоже заглушки. Доступны WebSocket/MessagePack, а не все способы транспорта SignalR.

**Что сделать.**
1. Для каждой команды записать точный формат, разрешённые роли/фазы, ответ, ошибки и клиентские обработчики; сравнить `Messages.ts`, `GameClient.ts`, `GameMessages.ts`, `messageProcessor.ts`, `game.ts` и эталон. Не совмещать `ISRIGHT` и `VALIDATE` без разбора разных форматов.
2. Реализовать апелляции как отдельный процесс с историей решения, правами, голосами и идемпотентным пересчётом. До этого не обещать работающую опцию апелляций.
3. Вести реальные показатели статистики на переходах, а не выводить нули/текущий счёт как статистику; проверить клиентскую схему и приватность.
4. Проверить все REST/SignalR методы реальным клиентом, ошибки и переподключение; отдельно решить, нужна ли совместимость с нативным клиентом и транспортами помимо WebSocket.

### P2. Пакеты и отображение

**Сейчас.** Парсер обрабатывает используемые v4/v5 данные и конвертирует часть v4; пользовательские сценарии и все метаданные пакета не гарантированы. **Что сделать.** Проверить атрибуты/значения по модели SI, создать небольшие воспроизводимые SIQ v4/v5 с Unicode, очень длинными именами, пробелами/URL-кодированием, коллизиями регистра, внешними URL и отсутствующими файлами. Сверить сообщения метаданных и безопасную распаковку; не включать личные или большие пакеты в репозиторий.

## 6. Как выполнять следующую задачу

1. Найти актуальную реализацию по пути/команде выше и написать точный сценарий: роли, фаза, вход, сообщения, таймеры, ожидаемые баллы и интерфейс. Исторический аудит использовать как указатель на исходники эталона, а не как готовое описание текущей ошибки.
2. Закрепить поведение отдельным регрессионным тестом **до** исправления; для гонок использовать Jest fake timers и проверять не только сообщение, но и отсутствие преждевременных/повторных сообщений другим игрокам.
3. Сверить соответствующий сценарий с зафиксированным кодом SI и форматами клиента. Если требования пользователя намеренно отличаются от SI — зафиксировать это явно, не менять UX молча.
4. Реализовать минимальный переход с проверкой прав, фазы, паузы, личности и идемпотентности. Новые таймеры и отложенные действия включать в существующую модель отмены/паузы; не применять глобальную отмену, уничтожающую независимый таймер раунда.
5. Дополнить unit- и, где затронут протокол, реальный SignalR/HTTP сценарий. Проверить людей и ботов, неверный и повторный ввод, паузу, реконнект, отключение и `MOVE` в затронутой фазе.
6. Обновить этот документ и соответствующие `docs/local-server.md`/аудит протокола: что стало поддерживаться, что остаётся ограниченным и какие проверки действительно проведены.

## 7. Проверки и воспроизведение

```bash
npm ci
npx tsc --noEmit -p server/tsconfig.json
npm test -- --runInBand --forceExit
npm run build-dev
npm run lint

# Отдельный терминал: интеграция требует работающий сервер на 8080 и пакет в библиотеке
npm run make-test-package
npm run server
# В другом терминале:
npm run test:server
```

Для сборки с локальными адресами дополнительно `npm run build-local`. Тесты движка: `test/serverReportedProblems.test.ts`, `serverDecisionGuards.test.ts`, `serverRoundAndAccess.test.ts`, `serverFinalRound.test.ts`, `serverFinalThemes.test.ts`, `serverMediaFiles.test.ts`, `serverLongMediaPaths.test.ts`; клиентские регрессии — `test/ClientController.test.ts` и остальные `test/`. Скрипты `test:server` перечислены в `package.json`; они проверяют в том числе реальные SignalR-сообщения, а не полноценную партию в графическом браузере.

На срезе `22df9ce` команда lint не проходила: 95 ошибок, включая известную проблему ESLint `parserOptions.project` для тестовых файлов, и 566 предупреждений. Это не освобождает от проверки новых ошибок. `--forceExit` позволяет завершить Jest, но может скрывать открытые таймеры/ресурсы; отдельно исследовать `--detectOpenHandles` и добиться нормального завершения. При новых запусках записывать фактические результаты, а не считать приведённые цифры постоянными.

Перед заявлением о совместимости дополнительно нужны: дифференциальный прогон с закреплённой SI, реальные SIQ и две-три отдельные браузерные сессии, а также проверка на Windows и при обрыве сети. Зафиксировать версию эталона, настройки, последовательность событий и отличия результата.
