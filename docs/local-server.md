# Локальный сервер SIGame (браузерные клиенты по IP)

В репозиторий добавлен собственный сервер на Node.js/TypeScript, который реализует тот же протокол,
что и центральные серверы SIGame. Благодаря этому обычный веб-клиент из `src/` подключается к нему
**из браузера по IP-адресу** — без установки десктопного приложения и без серверов vladimirkhil.com.

* Игровые хабы SignalR (MessagePack): `sihost` (комнаты и игровой процесс) и `sionline` (лобби).
* REST API: сведения о сервере, создание игры, вход по PIN.
* Раздача `.siq`-пакетов и всех медиафайлов (картинки, аудио, видео, HTML) с этого же сервера.
* Игровой движок: раунды, темы, выбор вопроса, кнопки, ответы, ставки, финальный раунд, таймеры, боты.

## Безопасность: только для доверенной сети

У локального сервера **нет входа и проверки личности**: кто дотянулся до порта, тот видит лобби,
может скачать загруженные пакеты и влиять на игру. Пароль комнаты и запрет зрителей ограничивают
только вход в конкретную игру и не защищают сервер.

* Не публикуйте порт в интернет и не пробрасывайте его на роутере.
* При `host: "0.0.0.0"` сервер печатает предупреждение при запуске; для игры только на своей
  машине укажите `host: "127.0.0.1"` в `server/config.json` или `SI_HOST=127.0.0.1`.
* Загруженные файлы (пакеты, аватары) раздаются как скачиваемые и не выполняются как страницы
  этого сайта; HTML-содержимое вопросов показывается в песочнице без доступа к приложению.
* Аватары принимаются только с расширениями изображений (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`,
  `.bmp`). Имя каталога загрузки не берётся из запроса: недопустимый `Content-MD5` отклоняется.

## Быстрый старт

```bash
npm install               # один раз
npm run make-test-package # (необязательно) создаёт server/packages/test-package.siq
npm run serve-local       # сборка веб-клиента + запуск сервера
```

Сервер напечатает адреса, например:

```
Локальный сервер SIGame запущен: http://192.168.1.10:8080
Откройте http://192.168.1.10:8080 в браузере, чтобы играть.
```

Ведущий и игроки открывают этот адрес в браузере (в том числе с телефонов в той же сети).
Игра создаётся автоматически для каждого пакета из `server/packages`, плюс можно создать новую
игру из веб-клиента (кнопка создания игры) или нажать «играть одному» — сервер сам добавит ботов.

Если веб-клиент уже собран (`npm run build-local`), достаточно `npm run server`.

## Сборка клиента, «зашитая» на локальный сервер

`npm run build-local` собирает клиент с `assets/config.local.js`:

* `serverUri = window.location.origin` — клиент всегда обращается к тому серверу, с которого загружен
  (localhost, IP в локальной сети, домен, preview-адрес — всё работает одинаково);
* отключены центральные сервисы (discovery, статистика, реестр приложений), поэтому клиент
  не «висит» на недоступных запросах.

Обычная сборка `npm run build-dev` / `build-prod` не меняется и по-прежнему использует
`assets/config.js` с центральным discovery.

## Пакеты и медиа

* `server/packages/*.siq` — локальная библиотека. Пакеты предлагаются клиенту при создании игры
  (`/api/v1/packages`); игры из них создаются по запросу клиента, а не автоматически.
  Автосоздание игр для всех пакетов включает параметр `startupGames: true` в `server/config.json`.
* Загрузка из браузера (создание игры из файла) сохраняется в `server/data/package/<hash>/<имя>.siq`.
* Медиафайлы распаковываются в `server/data/media/<packageId>/{Images,Audio,Video,Html}` и раздаются по
  `/package/<packageId>/<путь внутри пакета>`.
* Синхронизация: клиенты получают:
  * `ROUNDCONTENT` — список медиа раунда для предзагрузки;
  * `CONTENT2` — содержимое вопроса по мере показа (текст, картинка, аудио, видео, HTML);
  * `RIGHTANSWER` и контент ответа;
  * одинаковую длительность показа для всех участников (сервер ведёт тайминг сам).

  Адреса медиа абсолютные и строятся из того адреса, по которому клиент пришёл на сервер, поэтому
  игроки, зашедшие по `localhost` и по IP, видят одни и те же файлы.

  При поиске ссылок учитываются URL-кодирование, регистр и нормализация Unicode; неоднозначные
  имена не выбираются произвольно. Если файл всё ещё не найден, проверьте имя файла и ссылку в
  `content.xml` пакета, а также убедитесь, что файл присутствует в архиве. Внешние ссылки в пакете
  требуют доступности соответствующего сервера из браузеров участников.

### Тайминг медиа-вопроса

Длительность показа видео и звука берётся из самого файла (mp4/m4v/mov/m4a — по заголовку `mvhd`,
mp3 — по кадрам или `Xing`/`Info`, wav — по `data`/`byteRate`, ogg/opus — по гранулам последней
страницы). Если длительность определить не удалось, используется 3 секунды. Явный
`duration="hh:mm:ss"` в теге вопроса имеет приоритет.

Кнопка ответа на медиа-вопрос включается не сразу после показа контента, а по таймеру, который
идёт параллельно воспроизведению:

* указан `duration` — кнопка доступна после этого времени;
* `duration` нет — кнопка доступна на середине длительности файла.

Фоновое медиа (`placement="background"`) и звук фона таймер кнопки не задерживают. Показ ответа
не меняется: там сервер по-прежнему ждёт окончания медиафайла (`waitForMediaEnd`).

### Медиа и ответ игрока

Пока игрок отвечает, медиа вопроса стоит на паузе (клиент останавливает воспроизведение, когда
кнопка становится недоступной), и сервер помнит это состояние:

* ответ неверный — сервер отправляет `RESUME`, и воспроизведение продолжается с того же места;
* ответ отменён ведущим (`VALIDATE\n…\n-\n0`) — воспроизведение тоже продолжается;
* ответ верный — вопрос заканчивается, правильный ответ и контент ответа показываются как обычно;
* в вопросе нет медиа — `RESUME` не отправляется.

### Варианты ответа (`answerType=select`)

Варианты — часть вопроса, а не его концовки. В медиа-вопросе они появляются на экране вместе с
кнопкой ответа (в середине видео или после `duration`), а не после окончания воспроизведения:
иначе игрок успевает нажать кнопку и ответить, не увидев варианты. Выбор варианта по-прежнему
проверяет сервер, ведущий к нему не привлекается.

## Каталог данных и остановка

`server/data` содержит только копии: загруженные пакеты (`package`), распакованные медиа (`media`),
аватары (`avatars`) и временные загрузки (`uploads`). При остановке сервера (`Ctrl+C`, `SIGTERM`,
штатное закрытие) каталог очищается, поэтому следующий запуск начинается с чистого состояния.
Сам `server/data` не удаляется. Очистку можно отключить параметром `SI_CLEANUP_ON_SHUTDOWN=false`.

## Настройка

`server/config.json` (необязателен) или переменные окружения:

| Параметр | Env | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `port` | `SI_PORT` | `8080` | порт |
| `host` | `SI_HOST` | `0.0.0.0` | интерфейс (0.0.0.0 = доступ из локальной сети) |
| `publicBaseUrl` | `SI_PUBLIC_URL` | автоопределение по IP | адрес, который увидят игроки |
| `name` | — | `SIGame local server` | имя сервера в лобби |
| `packagesDir` | `SI_PACKAGES_DIR` | `server/packages` | библиотека пакетов |
| `dataDir` | `SI_DATA_DIR` | `server/data` | загруженные пакеты, медиа, аватары |
| `cleanupOnShutdown` | `SI_CLEANUP_ON_SHUTDOWN` | `true` | очищать `dataDir` при остановке сервера |
| `clientDir` | `SI_CLIENT_DIR` | `dist` | собранный веб-клиент |
| `maxPackageSizeMb` | — | `512` | максимальный размер пакета |
| `botNames` | — | список имён | имена ботов |
| `timeSettings` | — | значения SIGame | тайминги игры (в секундах) |

Пример `server/config.json`:

```json
{
  "port": 8080,
  "publicBaseUrl": "http://192.168.1.10:8080",
  "name": "Играем дома",
  "botNames": ["Иннокентий", "Александра", "Борис"]
}
```

Если сервер стоит за прокси/туннелем, `publicBaseUrl` можно не задавать: адрес берётся из заголовков
`Host`/`X-Forwarded-Host` того запроса, которым пришёл клиент.

## Проверка

```bash
npm run server     # в одном терминале
npm run test:server  # в другом
```

`test:server` запускает два e2e-скрипта:

* `server/scripts/smoke-test.js` — самописный SignalR-клиент на MessagePack проходит полный цикл:
  REST API → лобби → вход → готовность → старт → раунд → выбор вопроса → показ контента →
  скачивание медиа → нажатие кнопки → ответ → начисление очков → конец вопроса, плюс создание
  автоматической игры.
* `server/scripts/signalr-client-test.js` — проверка **настоящей** библиотекой `@microsoft/signalr`
  (той же, что использует браузер): negotiate, MessagePack-кадры, `TryGetGameInfo`, `JoinGame2`,
  keep-alive, чат, пауза, переход к следующему раунду, PIN и переподключение после обрыва связи.
* `server/scripts/answer-options-test.js` — вопрос с вариантами ответов: раскладка `ANSWER_OPTIONS`,
  показ вариантов A–D, выбор варианта по метке и начисление очков.
* `server/scripts/seats-test.js` — места и роли в лобби: количество столов соответствует настройкам
  создания игры, свободные места видны другим игрокам, вход ведущим и игроком работает,
  занятое место ведущего защищено.
* `server/scripts/host-rights-test.js` — права управляющего: `HOSTNAME` указывает на живого игрока,
  правила игры (`SET_OPTIONS`) принимаются и рассылаются всем, переход к выбранному раунду работает,
  а после выхода игрока остальные получают `DISCONNECTED` и освободившееся место можно занять.

Юнит-тесты движка и загрузчика пакетов: `npm run test:local-server`.

## Места (столы) в игре

* Сервер создаёт ровно столько мест, сколько запрошено: например, «3 игрока» — это три места игроков
  и ещё одно свободное место для того, кто присоединится, а не фиксированные 6 столов.
* Пустые места видны в лобби как offline-персоны с ролью `Player`, поэтому в карточке игры активна
  кнопка «подключиться игроком».
* Место ведущего по умолчанию ведёт сервер: пока его не занял живой игрок, оно отображается свободным
  и вход ведущим доступен. После входа место защищено от других игроков.
* Если все места заняты, а игра ещё не началась, сервер добавит стол новому игроку.
* Управляющий может добавить стол во время обычного раунда. Удаление стола и замена участника,
  запрошенные во время вопроса, применяются после его окончания, чтобы не нарушить индексы ответов;
  вытесненный подключённый участник остаётся зрителем. В финальном раунде изменение столов пока не поддерживается.
* Когда выходит последний подключённый человек, игра удаляется, даже если остались боты. Созданной
  комнате даётся 60 секунд на первое подключение; если никто не вошёл, она также удаляется.

## Права на управление игрой

Управляющий определяется в таком порядке:

1. живой подключённый ведущий (место ведущего занял человек);
2. создатель игры, если он подключён;
3. первый подключённый живой игрок.

Имя управляющего приходит в сообщении `HOSTNAME` и обновляется при каждом входе и выходе участника,
поэтому кнопки «старт», «дальше», смена правил, переход к раунду и пауза доступны тому, чьё имя совпадает
с `HOSTNAME`. Для игр, созданных через REST API, это создатель игры (он заходит ведущим). В автоматических
играх и в играх из локальной библиотеки место ведущего ведёт сервер, поэтому права получает первый
подключившийся живой игрок.

Правила игры (`SET_OPTIONS`: устные ответы, управляемая игра, ложные старты, частичный текст и картинки,
скорость чтения, время блокировки кнопки) применяются сразу, даже если игра уже идёт, сохраняются на сервере
и рассылаются всем участникам как `OPTIONS2`, поэтому их видят и те, кто подключился позже. Имена опций в
`OPTIONS2` — те, что понимает веб-клиент: `TimeForBlockingButton` уходит как `ButtonBlocking`,
`PartialImageTime` — как `PartialImage`, `UseApellations` — как `UseAppellations`.

## Устная игра

При `Oral = true` игрок нажимает кнопку и отвечает голосом — поле ввода не открывается.
Сразу после нажатия управляющий получает `ASK_VALIDATE` и оценивает ответ кнопками. Ведущему
лично отправляются правильные и неправильные ответы пакета через `QUESTION_ANSWERS`; игроки и
зрители их до раскрытия не получают. Если человеком управляет место игрока при ведущем-боте,
ему также доступны кнопки оценки, но подсказка с ответом игрокам не раскрывается.

Решение человека не имеет автоматического таймаута: окно проверки не должно исчезать само.
Боты по-прежнему отвечают и оцениваются автоматически.

## Финальный вопрос

Порядок шагов после того, как тема финала выбрана:

1. **Ставки.** Идёт таймер `timeForMakingStake`. Если все участники сделали ставку раньше, таймер
   пропускается и сервер сразу переходит к вопросу. Если таймер вышел, а ставки нет, считается
   минимальная ставка (1). Ставки скрыты от остальных до оценки ответа; игроки без очков в финале
   не участвуют (`PLAYER_STATE\nPass`).
2. **Показ вопроса.** Вопрос показывается как обычный: текст — по скорости чтения, медиа — по реальной
   длительности файла (или по `duration` из тега). Поле ввода ответа открывается сразу после первого
   элемента контента, то есть уже вместе с вопросом, но не раньше: игрок печатает, пока читает вопрос.
   Ответ, отправленный в этот момент, не теряется — он ждёт этапа проверки наравне с остальными.
3. **Ответы.** После показа вопроса запускается таймер `timeForFinalThinking`. Если все участники
   нажали «Отправить» раньше, таймер пропускается. По окончании таймера отправляется последний
   черновик (`ANSWER_VERSION`), даже если мысль не закончена.
4. **Проверка ведущим.** Ведущий получает ответы по очереди (`ASK_VALIDATE`) и оценивает их кнопками
   Да/Нет. После каждой оценки игроку начисляются или списываются очки, а ответ публикуется на карточке
   игрока (`PLAYER_ANSWER`) и в `ANSWERS`. Ответ всегда виден ведущему текстом, даже в устной игре:
   в финале ответы набирают, а не произносят. Если ведущего нет (или он сам играет в финале), решения
   принимает сервер — участник не оценивает собственный ответ.
5. **Итоги.** После оценки всех ответов показывается правильный ответ и контент ответа, затем
   `GAME_STATISTICS`: имя, количество верных и неверных ответов, заработанные и потерянные очки.
   Игроки в таблице идут по убыванию итогового счёта.

В устной игре поле с ответом игрока не показывается: ответ звучит голосом и остаётся пустым.
`ASK_VALIDATE` приходит с пустым ответом и признаком `+`, поэтому у ведущего шесть кнопок —
по три на правильный и на неправильный ответ:

| Кнопка | Сообщение | Итог |
| --- | --- | --- |
| «Да» | `VALIDATE\n\n+\n1` | `+цена` |
| «×0.5» | `VALIDATE\n\n+\n0.5` | `+цена/2` |
| «×2» | `VALIDATE\n\n+\n2` | `+цена×2` |
| «Пас» | `VALIDATE\n\n-\n0` | ответ отменяется: ни очков, ни штрафа, вопрос продолжается |
| «Нет» | `VALIDATE\n\n-\n1` | `−цена` |
| «×0.5» | `VALIDATE\n\n-\n0.5` | `−цена/2` |
| «×2» | `VALIDATE\n\n-\n2` | `−цена×2` |

Коэффициент применяется к цене вопроса и к штрафу (`noRisk` — вопрос без риска — штрафа не даёт),
неизвестное или отсутствующее значение считается равным `1`, поэтому старый клиент продолжает работать.
Сообщение старого формата `ISRIGHT\n<+|->\n<коэффициент>` тоже понимается.

## Варианты ответов (автоматическая проверка)

Вопрос с `answerType=select` проверяет сервер, а не ведущий: игрок нажимает кнопку, получает
`ANSWER select` и выбирает вариант. Присланная метка варианта (`A`–`D`) сверяется с правильным
ответом, очки начисляются или снимаются сразу, а `ASK_VALIDATE` ведущему не уходит — в том числе
в устной игре. Принимается только предложенный вариант (метка или его текст в пакете), а не
произвольный текст; на таком вопросе поле ввода не открывается.

## Ставки и выбор отвечающего

Параметр вопроса `price` (`<param name="price" type="numberSet">`) задаёт минимальную ставку:
к кнопке допускаются только игроки, у которых счёт **больше** минимума. Если таких нет, вопрос
завершается без ответа. Параметр `selectionMode` со значением `exceptCurrent` исключает из
отвечающих того, кто выбрал вопрос; остальные правила (передача хода, секретные вопросы) придут
отдельной итерацией.

## Пауза при выходе ведущего

Если живой ведущий выходит из игры, сервер сам ставит игру на паузу: таймеры и шаги замирают,
всем уходит `PAUSE +` и сообщение в чат. Когда ведущий возвращается на своё место, игра продолжается
с того же места (`PAUSE -`). Явная пауза управляющего (`PAUSE`) имеет приоритет: после неё игра
не возобновится сама. В лобби (до начала игры) пауза не ставится.

## Пас и завершение вопроса

Если все игроки, которые ещё могут отвечать, нажали «пас», вопрос завершается (`TIMER STOP`, `ENDTRY`,
правильный ответ и `QUESTION_END`) — и сразу после паса, и когда время нажатия истекло. Пасы не
переносятся на следующий круг нажатий.

## Таблица раунда

Таблица сохраняет исходную размерность: сыгранный вопрос не удаляет тему, а скрывает его цену
(`-1` в `TABLO2`), поэтому тема остаётся на месте до конца раунда.

## Аватары

Аватар, отправленный клиентом (`AVATAR\nimage\n<uri>`), сервер сохраняет и рассылает остальным участникам
как `AVATAR\n<имя>\nimage\n<uri>`, а новым участникам отдаёт вместе с полным состоянием игры.
Так как `INFO2` не содержит аватаров, клиент сохраняет уже известные аватары при обновлении состава
(вход, выход, изменение очков), иначе карточки теряли бы картинку.
Клиент отправляет аватар после входа в комнату и переподключения, поэтому аватары синхронизируются
между всеми клиентами; загрузка файлов доступна по `POST /api/v1/content/avatars`.

## Выход игрока из комнаты

* Когда клиент отключается (выход из комнаты, закрытие вкладки), сервер освобождает его место и рассылает
  остальным `DISCONNECTED` с именем участника, `PLAYER_COUNT`, обновлённые `SUMS` и `READY`, а в комнате
  (до старта игры) ещё и `INFO2`; лобби получает уведомление об изменении состава. Клиенты убирают
  участника с его места, и место снова становится свободным — его может занять другой игрок.
* Очки вышедшего игрока не сохраняются на его месте, но при возврате (перезагрузка страницы, повторный
  вход под тем же именем) сервер вернёт игрока на то же место с прежним счётом, если место ещё свободно.

## Структура

```
server/
  config.json.example     пример конфигурации
  packages/               локальная библиотека .siq
  scripts/                генератор тестового пакета и e2e-проверки (smoke, места, права ведущего, правила в игре)
  src/
    index.ts              точка входа: express, HTTP, WebSocket
    config.ts             конфигурация
    protocol.ts           имена сообщений протокола SIGame
    xml.ts                парсер XML (совместим с src/model/siquester)
    signalr/              кадры MessagePack, HubConnection, HubHost (negotiate + WebSocket)
    api/                  REST API, хранилище пакетов/медиа/аватаров, модели контрактов
    game/                 пакеты, библиотека, лобби, игровой движок
    hubs/                 sihost и sionline
```

## Ограничения

* Длинный polling SignalR не поддерживается: используется WebSocket (его поддерживают все актуальные браузеры).
* Голосовой чат, статистика и реестр приложений недоступны локально (запросы к ним отключены в
  `config.local.js` или отвечают пустыми данными). Аватары работают: они загружаются на локальный сервер
  (`/api/v1/content/avatars`) и рассылаются через игру.
* Сложные типы вопросов (кошки, аукционы со ставками ведущего, апелляции) обрабатываются упрощённо:
  обычные вопросы, вопросы с вариантами ответов, медиа, финальный раунд со ставками.

## Воспроизведение ответа и выбор хода

* При показе ответа видео и аудио без заданной длительности ждут сообщение клиента `ATOM` об окончании
  воспроизведения. Для неработающего или запрещённого браузером воспроизведения предусмотрен таймаут
  180 секунд; берётся первое корректное уведомление от подключённого участника. Медиа с явной
  длительностью показывается согласно ей. Это не гарантирует синхронность устройств.
* Управляющий может вручную назначить выбирающего кнопкой передачи хода, пока вопрос ещё не выбран.
  Сверка клиентских команд и известных ограничений — `client-server-protocol-audit.md`.

## Правила и управление шагами

Правила из запроса создания комнаты передаются в движок и в `OPTIONS2` (включая режим устной игры,
скорость чтения и настройки, показываемые в окне правил). Не все свойства полного SIOnline уже
реализованы в механике: например, фальстарт, частичный показ, апелляции и специальные типы вопросов
пока не имеют полной семантики, даже если их состояние отображается.

Пауза замораживает серверные шаги и клиентские таймеры раунда, нажатия и решения; после снятия
продолжается оставшееся время. «Дальше» завершает текущий ожидающий шаг, а не раунд. При ручной
проверке ответа живым ведущим она не закрывает окно проверки. Ведущий может выбрать вопрос за игрока.
